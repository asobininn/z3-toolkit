The proptest-z3 Book

Introduction

proptest-z3 extends proptest to generate test inputs whose elements have dependencies on one another. Define the input structure with proptest Strategies as usual, then express relationships between elements as constraints for Z3. By inverting constraints, you can generate inputs containing a specified number of violations and identify the locations of those violations. Relationships between elements are preserved during shrinking.

In this crate, the term name collectively refers to things used to identify an entity and refer to it elsewhere, such as variable names, table names, and row keys.

Who is this for?

This crate is intended for people testing software whose input elements depend on one another, such as compilers and static analyzers.

For example, it can help generate inputs that preserve consistency between definitions and references, as well as inputs that deliberately reference undefined names.

Prerequisites

This Book does not teach proptest or Z3 from scratch. The required background is:

  • proptest: The basics of property-based testing, including Strategy and proptest!. See the proptest Book.
  • Z3: A general understanding of SMT solvers. You do not need to know the Z3 API. See Programming Z3.
  • z3-toolkit: A companion crate by the same author that provides macros for writing constraints. The parts needed here are covered in Writing Constraints with z3-toolkit.

How to read this Book

Start with Getting Started to see a small working example. The Feature Guide explains each feature in detail, and Common Patterns shows constraint patterns useful when testing name resolution.

The API Reference documents public APIs and the semantics that are easy to overlook, especially evaluation order, steps, scopes, and labels.

Getting Started

In this chapter, we will write one normal-case test and one error-case test for a name resolver for a small language.

Setup

[dev-dependencies]
proptest = "1"
proptest-z3 = "0.1"

The Z3 library is also required. For installation instructions, see the z3 crate README.

The system under test

Consider a small language with one statement per line.

StatementMeaning
let xDefine x
let x = yUse y, then define x
print xUse x

The system under test is this language’s name resolver. It returns the positions where undefined names are referenced.

#![allow(unused)]
fn main() {
fn undefined_refs(source: &str) -> Vec<usize> {
    let offset = |word: &str| word.as_ptr() as usize - source.as_ptr() as usize;
    let mut defined = HashSet::new();
    let mut errors = vec![];
    for line in source.lines() {
        match line.split_whitespace().collect::<Vec<_>>()[..] {
            ["let", x] => {
                defined.insert(x);
            }
            ["let", x, "=", y] => {
                if !defined.contains(y) {
                    errors.push(offset(y));
                }
                defined.insert(x);
            }
            ["print", x] => {
                if !defined.contains(x) {
                    errors.push(offset(x));
                }
            }
            _ => unreachable!(),
        }
    }
    errors
}
}

This implementation is intentionally simple: definitions become visible after their statement is processed.

Build a Strategy for valid programs

We will build a program() Strategy that creates the shape of the input, then use constraints to ensure that every reference resolves to a visible definition.

#![allow(unused)]
fn main() {
use proptest::prelude::*;
use proptest_z3::prelude::*;

const VAR: Space = Space::new("var");

fn program() -> impl Strategy<Value = Skeleton> {
    prop::collection::vec(
        prop_oneof![
            Just(VAR.def()).boxed(),
            (VAR.def(), VAR.refer())
                .prop_map(|(x, y)| frag!("let ", x, " = ", y))
                .boxed(),
            VAR.refer().prop_map(|x| frag!("print ", x)).boxed(),
        ],
        1..8,
    )
    .prop_map(Skeleton::steps)
}

fn names() -> NameSpec {
    NameSpec::new().space(VAR, "[a-c]", 3)
}
}

The Strategy describes the possible statement shapes. fill assigns names to the holes while satisfying the rule.

#![allow(unused)]
fn main() {
proptest! {
    #[test]
    fn defined_names_resolve(
        s in program().fill(names(), |binds| bound(binds, VAR))
    ) {
        prop_assert_eq!(undefined_refs(&s.text), vec![], "{:?}", s);
    }
}
}

Generate an invalid input deliberately

A random valid program rarely contains an undefined reference. To test the error path, require exactly one reference to be invisible and mark that location.

#![allow(unused)]
fn main() {
#[derive(Debug, Clone, Copy, PartialEq)]
enum Bug {
    Unbound,
}

proptest! {
    #[test]
    fn undefined_names_are_reported(
        s in program().fill(names(), |binds| constraint!(
            exactly(1) {
                for i in binds.refs(VAR) {
                    binds.mark(i, Bug::Unbound, !visible(binds, i))
                }
            },
        ))
    ) {
        let [(hole, Bug::Unbound)] = s.marks::<Bug>()[..] else {
            panic!("expected exactly one marked hole");
        };
        let span = s.span(hole);
        prop_assert_eq!(undefined_refs(&s.text), vec![span.start], "{:?}", s);
    }
}
}

The constraint asks Z3 to generate an input with exactly one invisible reference. mark records which hole violates the rule, and Solved::span maps that hole to a byte range in the generated text.

This example is deliberately small. The Feature Guide explains how to represent scopes, name candidates, and more complex relationships.

Writing Constraints with z3-toolkit

proptest-z3 constraints are written with z3-toolkit’s constraint! macro. This chapter covers only the parts used by proptest-z3. proptest_z3::prelude::* re-exports the z3-toolkit prelude, so you do not need to add a separate import.

constraint! builds one z3::ast::Bool

constraint!(...) turns the conditions inside it into a single Z3 Bool. Since a rule passed to fill must return a Bool, the body of a rule will generally use constraint!(...).

#![allow(unused)]
fn main() {
program().fill(names(), |binds| constraint!(
    bound(binds, FUNC),
    !distinct_defs(binds, VAR),
))
}

Writing conditions

SyntaxMeaning
all { p, q, .. }All conditions hold
any { p, q, .. }At least one condition holds
exactly(n) { .. }Exactly n conditions hold
at_most(n) { .. } / at_least(n) { .. }At most / at least n conditions hold
!p, p && q, p || qNot, and, or
{ p } implies { q }If p, then q
distinct(xs)All values are distinct

Expanding with for and if

Inside constraint!, for and if can expand into per-item conditions. The following example means that exactly one reference to a VAR is not visible.

#![allow(unused)]
fn main() {
constraint!(
    exactly(1) {
        for i in binds.refs(VAR) {
            !visible(binds, i)
        }
    },
)
}

A for body can contain multiple conditions; each one contributes separately to the count. An if whose condition is a Rust bool is evaluated while building the constraint, so it can be used to select which terms to include.

For the complete syntax and more examples, see the z3-toolkit documentation.

Spaces and Holes

A hole is a blank that will be filled with a name later. Z3 decides which name goes into each hole based on the constraints. This section explains namespaces (Space), which define the groups of names a hole can draw from, and the information carried by each hole.

Define namespaces

A namespace is an independent set of names. Create a separate one for each category of name that is resolved independently, such as variables and functions.

#![allow(unused)]
fn main() {
const VAR: Space = Space::new("var");
const FUNC: Space = Space::new("func");
}

Space::new() takes an &'static str. This string is used as-is in diagnostic output, including counterexamples.

The same string name in different namespaces has no relationship to the other.

Hole roles

Each hole has a namespace and a role (Role). There are three roles:

RoleHow to create itMeaning
Role::DefVAR.def()Define a name
Role::UseVAR.refer()Reference a name
Role::KillVAR.kill()Delete a name; it is no longer visible afterward

A Use and a Kill hole are collectively called a reference, because both point to an existing name. The Binds and Rules section explains how to handle references together in constraints.

def(), refer(), and kill() each return a Strategy for a Frag containing one hole. To select the role dynamically, use hole(role).

#![allow(unused)]
fn main() {
VAR.hole(Role::Kill) // Same as VAR.kill()
}

Example: deletion and functions

Extend the language from Getting Started with del x and function declarations/calls such as fn f { ... } and call f. A Kill hole represents the name in del x. A function declaration introduces a Def, and a call introduces a Use. This lets the same visibility rules express variable references, function calls, and use-after-deletion errors.

Frag and Skeleton

Arrange holes and text to define the structure of an input. A structure under construction is called a Frag (fragment); the completed structure is a Skeleton.

  • Frag: A sequence of text and holes. Fragments can be joined with frag! or Frag::concat.
  • Skeleton: A sequence of Frag values divided into steps by Skeleton::steps.

Join pieces with frag!

frag! concatenates its arguments in order into one Frag.

#![allow(unused)]
fn main() {
(VAR.def(), VAR.refer()).prop_map(|(x, y)| frag!("let ", x, " = ", y))
}

The following values can be passed to frag!:

ValueExample
String"let "

Vec<Frag>Concatenates elements in order
Option<Frag>Adds nothing when None
Tuple (up to four elements)Concatenates elements in order
Text(x)A user-defined type implementing Display

Wrap a user-defined type in Text to insert its Display output as text.

#![allow(unused)]
fn main() {
#[derive(Debug, Clone, Copy)]
enum Op { Add, Sub }

impl Display for Op {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.write_str(match self {
            Op::Add => "+",
            Op::Sub => "-",
        })
    }
}

(VAR.refer(), prop_oneof![Just(Text(Op::Add)), Just(Text(Op::Sub))])
    .prop_map(|(x, op)| frag!("let a = ", x, " ", op, " b"))
}

Steps

A step is a unit at which definitions become visible; it corresponds roughly to a statement in a language.

Only Skeleton::steps, Frag::scope, and Frag::boundary create steps. Each element passed to these functions is closed as a separate step. frag!, Frag::concat, and Frag::join do not create steps. Concatenated fragments become one step when the surrounding construct closes them.

This distinction matters for statements such as let x = x: the right-hand-side reference is evaluated before the definition on the left becomes visible.

Scopes

Frag::scope(steps) creates a nested lexical scope. Each element in steps becomes a step in that scope. Definitions inside the scope are visible there and in nested scopes, but not outside it or in sibling scopes. Definitions from outer scopes remain visible inside, unless shadowed by a same-named inner definition.

The scope’s delimiters and whitespace are ordinary text and must be supplied by the caller.

Boundaries

Frag::boundary(steps) creates a scope marked as a boundary, suitable for a closure or function body. Name visibility is the same as for Frag::scope; the difference is that the number of boundaries between a reference and its target definition can be counted to detect captures.

Ordinary scopes do not count as boundaries. Blocks and boundaries can be nested freely.

NameSpec and Names

Names placed in holes are selected from a set of candidates defined per namespace. NameSpec describes how to generate those candidates.

Generate candidates with a regular expression

Use space(namespace, regex, count) to generate the requested number of distinct names matching a regular expression.

#![allow(unused)]
fn main() {
fn names() -> NameSpec {
    NameSpec::new()
        .space(VAR, "[a-c]", 3)
        .space(FUNC, "[a-c]", 3)
}
}

Chain .space calls when using multiple namespaces.

The candidates are generated by proptest. When a failing input is shrunk, the names can become shorter and simpler while still matching the regular expression.

Provide a Strategy

For candidates that cannot conveniently be described by a regular expression, pass a Strategy directly with space_with. This is useful, for example, when names must not overlap with reserved keywords.

#![allow(unused)]
fn main() {
const KEYWORDS: [&str; 5] = ["let", "print", "del", "fn", "call"];

fn names() -> NameSpec {
    let var = prop::collection::hash_set(
        "[a-z]{1,4}".prop_filter("keyword", |s| !KEYWORDS.contains(&s.as_str())),
        3,
    )
    .prop_map(|set| set.into_iter().collect::<Vec<_>>());
    NameSpec::new().space_with(VAR, var.boxed())
}
}

Fixed candidates

To keep the candidate set fixed, pass proptest’s Just Strategy to space_with. This is useful for reproducing a bug involving particular names.

#![allow(unused)]
fn main() {
fn names() -> NameSpec {
    NameSpec::new().space_with(VAR, Just(vec!["x".into(), "y".into()]).boxed())
}
}

The order of candidates supplied to space_with determines their indices. The solver uses those indices internally; constraints compare names by index rather than by their textual representation.

Binds and Rules

Relationships between names are expressed as rules. A rule is a function that takes &Binds and returns a Z3 Bool; it is passed to fill.

#![allow(unused)]
fn main() {
program().fill(names(), |binds| bound(binds, VAR))
}

This section describes Binds, the building blocks for rules, and predicates for common relationships.

Bind: hole indices

Binds lists the holes in a skeleton in evaluation order. Within a rule, a hole is referred to by its evaluation-order index i. A smaller index means earlier evaluation, so “a hole before i” can be expressed by comparing indices.

Hole indices can be selected by namespace and role. Each method returns indices in evaluation order.

SyntaxHoles returned
binds.defs(S)Def holes in namespace S
binds.uses(S)Use holes in namespace S
binds.kills(S)Kill holes in namespace S
binds.refs(S)References (Use and Kill) in namespace S
binds.of(S, role)Holes in namespace S with the given role

binds.name[i] is the Z3 Int representing the name assigned to hole i. Its value is a candidate index, so binds.name[p] == binds.name[q] means that holes p and q contain the same name.

#![allow(unused)]
fn main() {
// All VAR definitions must have distinct names.
fn no_redefinition(binds: &Binds) -> Bool {
    constraint!(
        distinct(binds.defs(VAR).map(|i| &binds.name[i])),
    )
}
}

Information known before solving

Some relationships are properties of the generated structure and are already known before Z3 solves the name assignments. Methods such as same_step, encloses, and boundaries_between return Rust values (bool or usize), not Z3 expressions. Use them to filter candidates or branch while building a constraint.

Common predicates

The rules module provides helpers for common name-resolution relationships:

  • visible(binds, i): the reference at i resolves to a visible, non-deleted definition.
  • killed(binds, i): the referenced name has a visible definition, but it has been deleted.
  • bound(binds, space): every reference in the namespace resolves to a visible definition.
  • unbound(binds, space, n): exactly n references in the namespace are not visible.
  • defined_in_same_step(binds, i): a definition with the same namespace and name exists in the same step, regardless of evaluation order.
  • distinct_defs(binds, space): all definitions in the namespace have different names, across the entire skeleton.
  • resolves_to(binds, i, k): reference i resolves specifically to definition k.
  • captured(binds, i): reference i resolves to a definition outside at least one boundary enclosing the reference.

See the API Reference for exact semantics, including how lexical scopes and Kill interact.

Labels

Rules can attach labels to generated inputs. Labels serve three purposes:

  • Record which hole was broken, and how (mark).
  • Classify generated inputs without adding a constraint (observe).
  • Name constraints so that rejection causes can be investigated (require).

Any type implementing Copy + Debug + PartialEq can be used as a label.

#![allow(unused)]
fn main() {
/// Kinds of violations introduced by a rule.
#[derive(Debug, Clone, Copy, PartialEq)]
enum Bug {
    Unbound, // Reference to an undefined name
    Killed,  // Reference to a deleted name
}

/// Classifications of generated inputs.
#[derive(Debug, Clone, Copy, PartialEq)]
enum Shape {
    Redefined, // A name is defined more than once
}
}

mark: record a broken location

binds.mark(i, kind, cond) returns cond unchanged and records that hole i is broken in way kind whenever cond holds.

#![allow(unused)]
fn main() {
|binds| constraint!(
    exactly(1) {
        for i in binds.refs(VAR) {
            binds.mark(i, Bug::Unbound, !visible(binds, i))
        }
    },
)
}

After solving, s.marks::<Bug>() returns a sequence of (hole, label) pairs. If exactly one hole is marked, a helper can make retrieving it convenient:

#![allow(unused)]
fn main() {
fn the_mark(s: &Solved) -> (Hole, Bug) {
    let [(hole, bug)] = s.marks::<Bug>()[..] else {
        panic!("expected exactly one mark");
    };
    (hole, bug)
}
}

mark is a record, not a constraint by itself. Its returned Bool must be included in the constraint (for example, inside exactly(1)) to enforce the condition.

observe: classify without constraining

binds.observe(kind, cond) records a classification when cond is true, but does not constrain which inputs can be generated. Use it to inspect the distribution of generated cases without changing that distribution.

require: name a constraint

binds.require(label, constraint) makes the condition mandatory and associates it with a name. If the combined constraints are unsatisfiable, the label can appear in Z3’s unsat core, helping identify why generation was rejected.

Use require to split a complicated rule into named parts when diagnosing repeated rejections.

Statistics and warnings

proptest-z3 tracks label statistics per thread. At the end of a test thread, labels that were declared but never occurred produce a warning, even if the test passes. This can reveal a supposedly covered violation that was never actually generated.

If one violation necessarily implies another, use given to state the precondition for classifying each one. This lets the two categories be generated and counted independently.

fill and Solved

fill combines a skeleton Strategy, candidate names, and a rule to produce a Strategy for inputs with their holes filled. Generated values are Solved.

#![allow(unused)]
fn main() {
proptest! {
    #[test]
    fn defined_names_resolve(
        s in program().fill(names(), |binds| bound(binds, VAR))
    ) {
        prop_assert_eq!(undefined_refs(&s.text), vec![], "{:?}", s);
    }
}
}

Choose a solving mode

Use fill_with to choose how holes are filled. By default, fill uses Fill::Greedy.

ModeBehavior
Fill::Greedy (default)Treat hints as assumptions. If they conflict with constraints, discard the last conflicting hint and solve again.
Fill::OptimalMaximize the number of hints that can be honored.

Both modes produce the same result from the same skeleton and hints. Re-solving the same input during shrinking is deterministic.

  • Fill::Greedy is fast. However, its choice of which hint to discard is not globally optimal, so it may discard more hints than Fill::Optimal.
  • Fill::Optimal tries to honor hints as much as possible, but can be slower for skeletons with many holes.

Use Fill::Greedy by default, and try Fill::Optimal if the generated names are distributed in an undesirable way.

Shrinking

When a test fails, proptest shrinks its input. proptest-z3 shrinks the structure, hints, and candidate names, and only tries inputs that satisfy the rule. If a shrunken input is unsatisfiable, that shrink direction is abandoned.

Shrinking does not necessarily reach a fixed point, so statements unrelated to the counterexample may remain in the final input.

Common Patterns

This chapter presents constraint patterns that are useful when testing name resolution.

Name-resolution boundary cases

A randomly generated valid program rarely hits situations where a resolver is likely to be wrong. Constrain the input to be valid with bound, then use any to ensure that a tricky situation occurs.

A same-named definition outside the current statement

let x
let x = x       // The right-hand side should refer to x from the first line.

A resolver that registers the left-hand x before resolving the right-hand side may incorrectly bind the right-hand side to itself.

program().fill(names(), |binds| constraint!(
    bound(binds, VAR),
    any { for i in binds.uses(VAR) { defined_in_same_step(binds, i) } },
))

Because bound requires every reference to be visible, and the same step contains a definition with the same name, the right-hand side must resolve to the outer definition.

Shadowing

let x
{
    let x
    print x     // Should refer to the inner x.
}

The outer x has the same name, so a resolver that does not respect lexical scopes may choose the outer definition.

/// Whether the definition resolved by reference `i` hides a same-named definition in an outer scope.
fn hides_outer(binds: &Binds, i: usize) -> Bool {
    let cases: Vec<Bool> = reaching_defs(binds, i)
        .flat_map(|k| reaching_defs(binds, i).map(move |q| (k, q)))
        .map(|(k, q)| constraint!(
            resolves_to(binds, i, k),
            binds.encloses(q, i),
            !binds.encloses(k, q),
            binds.name[k] == binds.name[q],
        ))
        .collect();
    constraint!(any { for c in cases { c } })
}

Use a rule like this to ensure that a reference resolves to an inner definition while a same-named outer definition also exists.

Deliberately generate an undefined reference

To exercise the error path, require exactly one invisible reference and mark it. See Labels for retrieving the marked hole and mapping it to a source span.

program().fill(names(), |binds| constraint!(
    exactly(1) {
        for i in binds.refs(VAR) {
            binds.mark(i, Bug::Unbound, !visible(binds, i))
        }
    },
))

Deleted names

To test use-after-deletion, ensure a Kill and a later reference share a name, with no later definition restoring visibility. Since Kill crosses scope boundaries, the shape of the generated program matters: the deletion must occur before the reference in evaluation order.

constraint!(
    any {
        for i in binds.refs(VAR) {
            killed(binds, i)
        }
    },
)

Captures

Use captured to select references that resolve across a boundary, such as a closure body. Ordinary lexical blocks do not count as boundaries. To test a closure that relays a capture through another closure, require a reference whose target is separated from it by two or more boundaries.

For the exact semantics of evaluation order, scopes, and deletion, see the API Reference.

Appendix: API reference

This lists the public API of proptest-z3 0.1.0, including signatures and semantics (especially the relation to scopes, steps and evaluation order). It is intended as a supplement to the main text, and as context when having an LLM write tests.

A.1 Before reading: two kinds of numbers

proptest-z3 has two kinds of numbers that point to holes. Mixing them up leads to wrong tests.

TypeOrderWhere used
number in evaluation orderusize (variable names i, k, j)evaluation order (A.2)inside constraints (Binds, rules)
number in text orderHole(pub usize)the order they appear in the output textafter solving (Solved)
  • Inside a constraint, i < k means “i is evaluated before k”. It is not before or after in the text.
  • There is no public API for getting a Hole from inside a constraint. If you need the position of a hole, put a mark on it with binds.mark(i, ..) and receive it as a Hole with s.marks() after solving.

A.2 Rules for steps, evaluation order and scopes

Steps

  • A step is “the unit at which definitions become visible”, and corresponds to a statement of the language.
  • Only three things create steps: Skeleton::steps(..) / Frag::scope(..) / Frag::boundary(..). Each of them closes each element passed to it as one step.
  • frag! / Frag::concat / Frag::join do not create steps. Joined fragments become one step together when they are closed outside.
  • Holes inside Frag::scope(..) / Frag::boundary(..) belong to the inner steps, not to the step of the outer statement.

Evaluation order

The evaluation order is determined by the following rules.

  1. Steps are ordered in text order.
  2. Within one step,
    • first: Use holes, and holes inside nested scopes contained in that step (in text order)
    • then: the step’s own Def and Kill holes (in text order)

Consequences:

  • The right-hand x (Use) of let x = x is evaluated before the left-hand x (Def) of the same statement, so it does not point to it.
  • del x (Kill) is evaluated after the Uses of the same statement.
  • When the Def of a statement and a scope contained in that statement are placed together, as in fn f { .. call f .. }, every hole inside the scope is evaluated before the definition of f. Therefore, by default, recursive calls are not visible. The same applies to boundaries (Frag::boundary).
  • The contents of a boundary (the body of a closure) are treated as evaluated at the position where they are written (the same as being called there). A Kill inside a boundary also affects references after the boundary.

Scopes

  • Frag::scope(steps) creates one nested scope. Scopes are lexical (static) nesting only.
  • A Def inside a scope is visible only from that scope and the scopes further inside it. It is not visible from outer or sibling scopes.
  • An outer Def is visible from inside. If the same name is defined inside, that one takes precedence inside (shadowing).
  • Scopes are not passed to z3. As Rust-side bools (Binds::encloses), they are used to narrow down candidates when building constraints.

Boundaries (closures and function bodies)

  • Frag::boundary(steps) creates a scope marked as a boundary. Use it for the bodies of closures and functions.
  • The visible range (encloses, visible, target and so on) is exactly the same as for Frag::scope. Boundaries do not change the result of name resolution.
  • The only difference is that you can count how many boundaries a reference crosses to reach its definition (Binds::boundaries_between). This is used to decide “captures” (captured).
  • Ordinary scopes (Frag::scope) are not counted when crossed. Blocks inside boundaries and boundaries inside blocks can both be nested freely.

NameSpec / Names—candidates are per namespace, not per scope

Kill crosses scopes. If there is even one Kill of the same name in the same namespace between definition k and reference i (in evaluation order), k is not visible from i. Which scope that Kill is in does not matter.

  • If you del a in an inner scope, the outer a also disappears. This is the same even when there is an a of the same name inside and del a points to that one.
  • A del a inside a closed sibling scope also affects later references to a.
  • If there is a Def of the same name after the Kill, that definition is newly visible. However, the range where it is visible is only inside the scope of that Def.

distinct_defs crosses scopes. !distinct_defs(binds, S) means “there is a pair of definitions with the same name somewhere”, and is not limited to reassignment in the same scope. If you want to forbid or allow only redefinitions within the same scope, narrow down the pairs of definitions with binds.encloses and binds.same_step and write it yourself with constraint!.

resolves_to(i, k) is Solved::target turned into a constraint. After solving, target(hole of i) == Some(hole of k) only when resolves_to(i, k) is true. visible(i) is equivalent to “resolves_to for some element of reaching_defs(i)”.

The three states of a reference

Reference i is in exactly one of the following. !visible is the union of “deleted” and “undefined”.

StateExpression
visiblevisible(binds, i)
deletedkilled(binds, i)
undefined (no visible definition anywhere)(!visible(binds, i)).given([!killed(binds, i)])

“Undefined” also includes the case where there are only definitions not visible from outside (inside a closed scope, inside a sibling scope). If you want to distinguish “points to a definition out of scope” from “there is no definition anywhere”, narrow down binds.defs(..) with encloses and write it yourself with constraint!.

Common forms

#![allow(unused)]
fn main() {
// positive case
bound(binds, VAR)

// positive case including redefinition (including same names across scopes)
constraint!(bound(binds, VAR), !distinct_defs(binds, VAR))

// negative case: exactly one reference is not visible. Mark that hole
constraint!(exactly(1) { for i in binds.refs(VAR) {
    binds.mark(i, Bug::Unbound, !visible(binds, i))
} })

// self reference (`let x = x`)
constraint!(all { !visible(binds, i), defined_in_same_step(binds, i) })

// definition k is used (for detecting unused definitions; add `!` for unused)
constraint!(any { for i in binds.refs(VAR) { resolves_to(binds, i, k) } })

// mark captured references (a classification, so not made a constraint)
for i in binds.refs(VAR) {
    binds.mark(i, Captured, captured(binds, i));
}

// at least one capture that crosses two or more boundaries (relayed by an outer closure)
fn relayed(binds: &Binds, i: usize) -> Bool {
    let cases: Vec<Bool> = reaching_defs(binds, i)
        .filter(|&k| binds.boundaries_between(k, i) >= 2)
        .map(|k| resolves_to(binds, i, k))
        .collect();
    Bool::or(&cases)
}
constraint!(bound(binds, VAR), any { for i in binds.refs(VAR) { relayed(binds, i) } })
}

When you want to change the condition by the number of boundaries, do not use captured; like relayed, narrow down reaching_defs with boundaries_between and combine resolves_to.

A.8 Marks, classification and named constraints (labels)

Label

Every type that is Copy + Debug + PartialEq + Send + Sync + 'static is a Label (blanket implementation). Use your own enums or &'static str.

  • The name of a label is the string itself for &'static str, and the Debug output otherwise. Statistics (label_stats) and the tally of rejections (take_rejections) are counted by this name. Two labels of different types are counted as the same if their names are the same.
  • marks::<L>() / labels::<L>() filter by the type L.

Recording (methods of Binds)

A.9 Passing to proptest

FillExt

Implemented for every type that implements Strategy<Value = Skeleton>.

SignatureContents
fn fill<R>(self, names: NameSpec, rule: R) -> Filled<Self, R>fill_with(Fill::Greedy, ..)
fn fill_with<R>(self, fill: Fill, names: NameSpec, rule: R) -> Filled<Self, R>chooses how to solve

R: Fn(&Binds) -> Bool + 'static. When using outside values, make it a move closure.

Filled<S, R> is a Strategy<Value = Solved>.

Fill

ValueContents
Fill::Greedy (default)solves with the hint of each hole as an assumption. On a conflict, drops the hint that is last in evaluation order within the unsat core and solves again. Uses a QF_LIA solver. Deterministic and fast
Fill::Optimalmaximizes the number of hints kept (Optimize). Faithful, but slow with many holes

In Greedy, preferences are given up starting from holes later in evaluation order, so names are closer to the hints for holes evaluated earlier.

Behavior of generation and shrinking

  • Generation: makes a skeleton and candidates, and remakes them if they cannot be solved (unsat). One remake is one local reject in proptest, and the test is aborted when the limit (max_local_rejects) is exceeded.
  • Shrinking: when a shrunk input cannot be solved, it goes back as “the failure cannot be reproduced in that direction” and searches another direction.
  • If the solved result (the text and the marks and labels) is the same as one tested before, the test is not called. If the skeleton and candidates are the same, it is not solved again.
  • Shrinking is not run to a fixed point. Lines unrelated to the counterexample may remain.

Rules of target (the same as A.2):

  • The candidates are those in reaching_defs (lexical) with the same name and with no Kill of the same name (in any scope) in between.

  • What a Kill actually deletes is every definition of the same name. target returns only one of them (the one chosen by the rule above).
  • To write the same thing inside a constraint, use resolves_to(binds, i, k) (A.7). Boundaries do not change the result of target.

A.11 Solving directly: Skeleton::solve

#![allow(unused)]
fn main() {
fn solve(&self, names: &Names, fill: Fill, rule: impl Fn(&Binds) -> Bool) -> Result<Solved, Failure>
}

Solves one skeleton without going through proptest. Used in unit tests and when checking generated inputs.

#![allow(unused)]
fn main() {
let skeleton = Skeleton::steps([frag!["def ", Frag::hole(VAR, Role::Def, Hint(0))]]);
let names = Names::default().with(VAR, ["a", "b"]);
let solved = skeleton.solve(&names, Fill::Greedy, |binds| bound(binds, VAR))?;
}
  • If it cannot be solved, Err(Failure::Unsat { core }) (core is the names of require); if it cannot be decided, Err(Failure::Unknown { reason }).
  • It panics if the candidates of a namespace that has holes in the skeleton are empty (no names for space ..).
  • It does not count label statistics (they are only counted at generation time in fill).

A.12 What is used from z3-toolkit

Inside rules, z3-toolkit’s constraint! is used (it comes in with the prelude). The forms used in proptest-z3’s examples and tests are as follows. For the exact syntax, see the documentation of z3-toolkit.

FormMeaning
constraint!(e1, e2, ..)all hold (conjunction)
constraint!(x == y) / constraint!(x in 0..n)comparison / range
all { .. } / any { .. }conjunction / disjunction
exactly(n) { .. } / at_most(n) { .. }exactly n / at most n are true
{ for i in iter { e1, e2 } }lists terms by iteration. If multiple terms are written in the body, all of them are counted
if cond { e } else { e } (Rust bool)chooses terms by a condition fixed at generation time
e1 || e2,!edisjunction / negation

z3 Bools can also be built directly: bound(binds, VAR) & bound(binds, FUNC), Bool::from_bool(true) (no constraint), Bool::or(&[..]) (false if empty), Bool::and(&[..]) (true if empty).

A.13 Conditions that lead to rejection or panic

SituationResult
the rule is unsat (e.g. exactly(1) { for i in binds.refs(..) .. } on a skeleton with no references)a local reject during generation. Treated as “passed” during shrinking
local rejects exceed max_local_rejectsthe test is aborted
a namespace that has holes in the skeleton is not registered in NameSpecpanic (no names for space ..)

the candidates of space_with contain an empty string or duplicatespanic
the regular expression of NameSpec::space is invalidpanic

When rejections are frequent, give names to the constraints with require and look at take_rejections(). Often the shape (strategy) cannot satisfy the conditions, so prepare shapes that can satisfy them on the strategy side (e.g. in a use-after-delete test, make sure to build a shape that places a use after del).

  • A proptest! test panics when rejections exceed the limit, and cannot proceed to take_rejections() afterwards. Generate by calling new_tree directly on a TestRunner, and tally the results
  • A set with only one name is almost always caused by the shape (it is rejected even if the other constraints are removed). A contradiction in the rule itself appears as a set that no shape can satisfy. The most frequent set is not necessarily the cause
  • The sets returned by Z3 are not necessarily minimal. Remove suspicious constraints one at a time to confirm
#![allow(unused)]
fn main() {
use proptest::test_runner::TestRunner;
use proptest_z3::take_rejections;

#[test]
fn why_rejected() {
    let strategy = program().fill(names(), rule);
    let mut runner = TestRunner::default();
    for _ in 0..50 {
        if strategy.new_tree(&mut runner).is_err() {
            break; // rejections exceeded the limit
        }
    }
    for (core, count) in take_rejections() {
        eprintln!("{count:>5} {core:?}");
    }
}
}

A.14 Checklist when writing tests

Points where an LLM tends to make mistakes when writing tests.

  • Numbers inside constraints are in evaluation order; the Hole of Solved is in text order. A Hole cannot be made inside a constraint.
  • The right-hand side of a statement does not see the definition on the left-hand side. The Def of a statement is not visible from the scopes contained in that statement either (by default, recursion is not possible).
  • Kill deletes every definition of the same name across scopes.
  • distinct_defs counts across scopes. !distinct_defs means “there is a definition of the same name somewhere”, not necessarily a reassignment in the same scope.
  • Frag::boundary does not change the visible range. Outer definitions are normally visible from inside a closure. Whether it is a capture is decided with captured / boundaries_between.
  • boundaries_between does not count ordinary scopes (Frag::scope). Pointing to an outer definition from inside a block is not a capture.
  • The contents of a boundary are treated as evaluated at the position where they are written. A Kill in a closure body also affects later references.
  • To distinguish “undefined” from other violations, add preconditions with given. Otherwise, some kind may never be generated (you can notice it from the warning).
  • If you forget to put the return value of mark into a constraint, it is only a record.
  • exactly(1) in a negative case is unsat if the skeleton has no target hole at all. Make sure the target hole is built on the shape side.
  • Write the checker for positive cases (the expected values of tests) independently of rules. If written with the same semantics, it shares the same mistakes.
  • The closure of a rule is 'static. Bring outside values in with move.
  • require returns no value, so do not write it inside constraint!. Call it in the body of the rule, and do not also put the same constraint in the return value.
