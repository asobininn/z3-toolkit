The proptest-z3 Book(日本語版)

はじめに

proptest-z3 は、要素間の依存関係を持つテスト入力を生成するための、proptest の拡張です。入力の構造は通常どおり proptest の Strategy で定義し、要素どうしの関係は Z3 の制約で指定します。制約を反転することで、指定した数の違反を含む入力を生成でき、違反した箇所も特定できます。縮小時にも要素間の関係は保たれます。

本クレートでは、変数名やテーブル名、行のキーのように、ある対象を識別し、別の場所から参照するために使われるものを総称して「名前」と呼びます。

対象読者

コンパイラや静的解析器など、入力の要素間に依存関係があるソフトウェアをテストしたい人向けです。

例えば、定義と参照の整合性を保った入力や、意図的に未定義の名前を参照する入力を生成したいときに役立ちます。proptest-z3 は、このような入力の生成を支援します。

前提知識

この Book では、proptest と Z3 の使い方を説明しません。必要な範囲は次の通りです。

  • proptest: Strategy、proptest!などのプロパティベーステストの考え方。 proptest bookにて学ぶことができます。
  • Z3: SMTソルバの概要を理解していること。Z3自体の使い方を知っている必要はありません。詳しく知りたい方はこちら → Programming Z3
  • z3-toolkit: 同じ作者のクレートで、制約を書くマクロを提供します。z3-toolkitで制約を書くで、必要な部分を説明しています。

このクレートが扱う範囲

proptest-z3 は、定義と参照を含む小さなテスト入力のためのクレートです。本クレートで使用される「名前」とは、変数名やテーブル名、行のキーのように、作られてから別の場所で指されるものを広く指します。

  • 扱える関係は、名前どうしの等しさだけです。型や値の条件は constraint! で足せますが、整数などの値そのものを Z3 に選ばせる機能はまだありません。
  • スコープは、ブロックのような字句的な入れ子だけを扱います。
  • 入力の構造は proptest が決めるため、構造が制約を満たせないと生成が棄却されます。棄却が多いときは、条件を満たせる構造を Strategy の側で用意してください。
  • 穴が多いほど、制約を解くのに時間がかかります。

Getting Started

この章では、小さな言語の名前解決器を例に、正常系と異常系のテストを1本ずつ書きます。

準備

[dev-dependencies]
proptest = "1"
proptest-z3 = "0.1"

Z3 のライブラリが必要です。入れ方については z3 クレートのREADME を参照してください。

テストする対象

1行に1文の、小さな言語を考えます。

文意味
let xx を定義する
let x = yy を使ってから x を定義する
print xx を使う

テストする対象は、この言語の名前解決器です。未定義の名前を参照した位置を返します。

#![allow(unused)]
fn main() {
fn undefined_refs(source: &str) -> Vec<usize> {
    let offset = |word: &str| word.as_ptr() as usize - source.as_ptr() as usize;
    let mut defined = HashSet::new();
    let mut errors = vec![];
    for line in source.lines() {
        match line.split_whitespace().collect::<Vec<_>>()[..] {
            ["let", x] => {
                defined.insert(x);
            }
            ["let", x, "=", y] => {
                if !defined.contains(y) {
                    errors.push(offset(y));
                }
                defined.insert(x);
            }
            ["print", y] => {
                if !defined.contains(y) {
                    errors.push(offset(y));
                }
            }
            ref other => panic!("unexpected line: {other:?}"),
        }
    }
    errors
}
}

1. 骨格を書く

名前を書く場所に、文字列の代わりに「穴」を置きます。穴は「後で名前が入る空欄」です。どの穴にどの名前が入るかは、制約をもとに Z3 が決定します。

VAR は名前空間(Space)です。変数と関数のように、互いに独立した名前の集まりごとに1つ作ります。

  • VAR.def(): 名前を定義する穴
  • VAR.refer(): 名前を参照する穴
#![allow(unused)]
fn main() {
use proptest::prelude::*;
use proptest_z3::prelude::*;

const VAR: Space = Space::new("var");

fn program() -> impl Strategy<Value = Skeleton> {
    prop::collection::vec(stmt(), 1..8)
        .prop_map(|stmts| Skeleton::steps(stmts.into_iter().map(|s| frag![s, "\n"])))
}

fn stmt() -> impl Strategy<Value = Frag> {
    prop_oneof![
        VAR.def().prop_map(|x| frag!["let ", x]),
        (VAR.def(), VAR.refer()).prop_map(|(x, y)| frag!["let ", x, " = ", y]),
        VAR.refer().prop_map(|y| frag!["print ", y]),
    ]
}
}

frag! は、文字列を穴を並べて1つの断片(Frag)にします。Skeleton::steps は、要素を1つずつステップとして区切ります。言語の「文」に当たる単位で区切ってください。

2. 名前の候補を決める

穴に入る名前は、ユーザーが用意した候補の中から選ばれます。NameSpec は、名前空間ごとに候補の作り方を決めるものです。

#![allow(unused)]
fn main() {
fn names() -> NameSpec {
    // [a-c] に合う、互いに異なる名前を3個
    NameSpec::new().space(VAR, "[a-c]", 3)
}
}

3. 正常系: 定義済みの名前だけ使用する

.fill(names, rule) で、穴を埋めた入力の Strategy になります。rule は、守らせたい関係を返す関数です。

bound(VAR) は「VAR のすべての参照の穴に、それより前の文で定義された名前が入る」という制約です。

#![allow(unused)]
fn main() {
proptest! {
    #[test]
    fn defined_names_resolve(s in program().fill(names(), |binds| bound(binds, VAR))) {
        prop_assert_eq!(undefined_refs(&s.text), vec![], "{:?}", s);
    }
}
}

4. 異常系: 1箇所だけ未定義にする

正常系の制約を反転させると異常系になります。!visible(binds, i) は「参照 i が、見えていない名前を指す」です。それがちょうど1つあるように書きます。

#![allow(unused)]
fn main() {
#[derive(Debug, Clone, Copy, PartialEq)]
struct Undefined;

proptest! {
    #[test]
    fn undefined_name_is_reported_where_it_is(s in program().fill(names(), |binds| constraint!(
        exactly(1) {for i in binds.refs(VAR) {
            binds.mark(i, Undefined, !visible(binds, i))
        }},
    ))) {
        eprintln!("{}", s.text);
        let [(hole, Undefined)] = s.marks::<Undefined>()[..] else {panic!("{s:?}")};
        prop_assert_eq!(undefined_refs(&s.text), vec![s.span(hole).start], "{:?}", s);
    }
}
}

mark は穴に印をつけるためのものです。binds.mark(i, Undefined, 条件) と書くと、生成された入力でその条件が成り立っていれば、穴 i に Undefined という印が付きます。

5. バグを見つける

名前解決器によくあるバグを入れてみます。let x = y で、右辺を調べる前に左辺を定義してしまうバグです。

#![allow(unused)]
fn main() {
["let", x, "=", y] => {
    defined.insert(x);
    if !defined.contains(y) {
        errors.push(offset(y));
    }
}
}

テストを実行すると、異常系が失敗し、入力が縮められます。

test undefined_name_is_reported_where_it_is ... FAILED
test defined_names_resolve ... ok

minimal failing input: s = Solved{
  0| let b
  1| let a = a
 marks: Undefined @ 14..15 `a`
}

2行目の右辺の a は未定義のはずですが、名前解決器はエラーを報告しませんでした。

正常系のテストが通っていても、本来エラーにすべき入力を受け入れてしまうバグは残り得ます。異常系の入力も生成することで、こうしたバグを検出できます。

縮小について: 反例に、バグと関係のない let b が残っています。proptest-z3 の縮小は、名前の関係を保ちながら入力を小さくしますが、これ以上縮まなくなるまで繰り返すことはしません。原因が読み取れる大きさまで縮めば十分という方針で、その分テストの実行が速く終わります。残った行も、制約を満たす正しい入力の一部です。

z3-toolkit で制約を書く

proptest-z3 の制約は、z3-toolkit の constraint! マクロで書きます。この章では、proptest-z3 で使う部分だけを説明します。proptest_z3::prelude::* が z3-toolkit の prelude を再エクスポートしているので、依存を足す必要はありません。

constraint! は z3::ast::Bool を1つ作る

constraint!(..) は、中に書いた条件からZ3の Bool を1つ作ります。fill に渡す規則は Bool を返す関数なので、規則の本体は基本 constraint!(..) を使用します。

#![allow(unused)]
fn main() {
program().fill(names(), |binds| constraint!(
    bound(binds, FUNC),
    !distinct_defs(binds, VAR),
))
}

条件の書き方

書き方意味
all { p, q, .. }すべて成り立つ
any { p, q, .. }どれかが成り立つ
exactly(n) { .. }ちょうど n 個が成り立つ
at_most(n) { .. } / at_least(n) { .. }n 個以下 / n 個以上が成り立つ
!p、p && q、p || q否定、かつ、または
{ p } implies { q }p ならば q
distinct(xs)すべて異なる

for と if で展開する

constraint!内では for と if が使用でき、要素ごとの条件に展開されます。次の例は「VARの参照のうち、見えていないものがちょうど1つ」です。

#![allow(unused)]
fn main() {
constraint!( exactly(1) { for i in binds.refs(VAR) {
    !visible(binds, i)
} })
}

if はRustの bool で条件を絞ります。

constraint! は z3 の Bool を返す式なので、長くなった制約は &Binds を受け取って Bool を返す関数に切り出せます。次の例は「VARの名前は再定義がない」です。

#![allow(unused)]
fn main() {
fn no_redefinition(binds: &Binds) -> Bool {
    let defs: Vec<_> = binds.defs(VAR).collect();
    constraint!(
        all { for &p in &defs { for &q in &defs {
            if p < q {
                binds.name[p] != binds.name[q]
            }
        } } },
    )
}
}

この例では、distinct を使うと、より簡潔に書けます。

#![allow(unused)]
fn main() {
fn no_redefinition(binds: &Binds) -> Bool {
    constraint!(
        distinct(binds.defs(VAR).map(|i| &binds.name[i])),
    )
}
}

Space と穴

穴は「後で名前が入る空欄」です。どの穴にどの名前が入るかは、制約をもとにZ3が決めます。この節では、穴を作るための名前空間(Space)と、穴が持つ情報を説明します。

名前空間を作る

名前空間は互いに独立した名前の集まりです。変数と関数のように、別々に解決される名前ごとに1つ作ります。

#![allow(unused)]
fn main() {
const VAR: Space = Space::new("var");
const FUNC: Space = Space::new("func");
}

Space::new() には &'static str を渡します。この文字列は、反例の表示などにそのまま使用されます。

名前空間が違えば、同じ名前の文字列でも関係を持ちません。

穴の役割

穴は名前空間と役割(Role)を持ちます。役割は次の3つです。

役割作り方意味
Role::DefVAR.def()名前を定義する
Role::UseVAR.refer()名前を参照する
Role::KillVAR.kill()名前を削除する。以降、その名前は見えなくなる

UseとKillの穴をまとめて参照と呼びます。どちらも既にある名前を指す穴だからです。制約の中で参照をまとめて扱う方法は、Binds と規則で説明します。

def() / refer() / kill()は、穴を1つだけ含む Frag の Strategy を返します。役割を引数で選びたいときは hole(role) を使用します。

#![allow(unused)]
fn main() {
VAR.hole(Role::Kill)   // VAR.kill() と同じ
}

例: 削除と関数を追加する

Getting Started の言語に、del x と、関数の fn f / call f を追加します。

#![allow(unused)]
fn main() {
fn stmt() -> impl Strategy<Value = Frag> {
    prop_oneof![
        VAR.def().prop_map(|x| frag!["let ", x]),
        (VAR.def(), VAR.refer()).prop_map(|(x, y)| frag!["let ", x, " = ", y]),
        VAR.refer().prop_map(|y| frag!["print ", y]),
        VAR.kill().prop_map(|x| frag!["del ", x]),
        FUNC.def().prop_map(|f| frag!["fn ", f]),
        FUNC.refer().prop_map(|f| frag!["call ", f]),
    ]
}
}

テスト対象の名前解決器も、del と関数を扱えるように広げてください。

削除後の参照を作りたいとき: 「削除した名前を使う」入力は、del の後に同じ名前空間の参照が来る構造からしか作れません。構造は proptest が決めるので、del の出現率が低い Strategy では、制約を満たせずに棄却が増えます。このような場合は、del を出やすくするか、del の後に参照を置く文を Strategy の側で用意してください。

ヒント

各穴は、名前とは別にヒントを持ちます。ヒントは「候補の何番目の名前が欲しいか」を表す0～1の固定小数点数(Hint(u16))で、proptest が決めます。

Z3 は制約とぶつからない限りヒントどおりの名前を選びます。そのため、制約で決まらない部分の名前は proptest によってばらつきます。

ヒントは縮小にも使用されます。縮小するとヒントは 0 に寄るので、穴に入る名前の候補も先頭に寄っていきます。反例で同じ名前が繰り返し使われやすいのはこのためです。

ヒントを利用者が直接扱う必要はありません。穴をdefs()などで作れば、ヒントも一緒に作られます。

Frag と Skeleton

穴と文字列を並べて入力の構造を作ります。組み立て中のものを Frag(断片)、完成したものを Skeleton と呼びます。

  • Frag: 文字列と穴の並び。frag! や Frag::concat でつなげることができる
  • Skeleton: Skeleton::stepsで、Frag の列をステップに区切ったもの

frag! でつなげる

frag! は渡したものを順につなげて1つの Frag にします。

#![allow(unused)]
fn main() {
(VAR.def(), VAR.refer()).prop_map(|(x, y)| frag!("let ", x, " = ", y))
}

frag! に渡せる値は次のとおりです。

渡せるもの例
文字列"let "
数値42
Frag(穴を含む)x、frag![..]
Vec<Frag>要素を順につなげる
Option<Frag>None なら何も足さない
タプル(4要素まで)要素を順につなげる
Text(x)Display を実装したユーザ型

ユーザの型は Text で包むと Display の結果が文字列として入ります。

#![allow(unused)]
fn main() {
#[derive(Debug, Clone, Copy)]
enum Op { Add, Sub, }

impl Display for Op {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.write_str(match self { Op::Add => "+", Op::Sub => "-", })
    }
}

(VAR.refer(), prop_oneof![Just(Op::Add), Just(Op::Sub)], VAR.refer())
    .prop_map(|(lhs, op, rhs)| frag!(lhs, " ", Text(op), " ", rhs))
}

手で組む

frag! を使わずに、関数で組み立てることもできます。

関数内容
Frag::text(s)文字列だけの Frag
Frag::hole(..)穴1つの Frag
Frag::concat(frags)順につなげる
Frag::join(sep, frags)間に区切りを挟んでつなげる

Frag::join は、引数の並びのような区切りのある列に使います。

#![allow(unused)]
fn main() {
prop::collection::vec(VAR.refer(), 0..4)
    .prop_map(|args| frag!["print(", Frag::join(", ", args), ")"])
}

ステップ

Skeleton::steps は、渡した列の要素を1つずつステップとして区切ります。ステップは、定義した名前が見えるようになる単位です。言語の「文」に当たる単位で区切ってください。

#![allow(unused)]
fn main() {
fn program() -> impl Strategy<Value = Skeleton> {
    prop::collection::vec(stmt(), 1..8)
        .prop_map(|stmts| Skeleton::steps(stmts.into_iter().map(|s| frag![s, "\n"])))
}
}

評価順

穴は、テキストの順ではなく評価順に並べて扱われます。評価順は次のように決まります。

  • ステップは、並んでいる順に評価される
  • ステップの中では、Use の穴が先、Def と Kill の穴が後に評価される

そのため、let x = y の y は x より先に評価されます。let a = a の右辺の a は、同じ文の左辺の a を指しません。Rust の let と同じ振る舞いです。

制約は、この評価順をもとに書きます。詳しくは Binds と規則 で説明します。

スコープ

Frag::scope は、入れ子のスコープを作ります。渡した列の要素は Skeleton::steps と同じようにステップとして区切られ、中で定義した名前はスコープの外から見えません。

ブロック { .. } を足すと、次のようになります。

#![allow(unused)]
fn main() {
fn stmt() -> impl Strategy<Value = Frag> {
    let simple = prop_oneof![
        VAR.def().prop_map(|x| frag!["let ", x]),
        (VAR.def(), VAR.refer()).prop_map(|(x, y)| frag!["let ", x, " = ", y]),
        VAR.refer().prop_map(|y| frag!["print ", y]),
    ];
    simple.prop_recursive(3, 16, 4, |inner| {
        prop::collection::vec(inner, 1..4).prop_map(|stmts| {
            frag!["{\n", Frag::scope(stmts.into_iter().map(|s| frag![s, "\n"])), "}"]
        })
    })
}
}

外側から見ると、ブロック全体が1つのステップです。ブロックの中の文は、それぞれがスコープの中のステップになります。

  • ブロックの中からは、ブロックより前に外で定義された名前が見える
  • ブロックの中で定義した名前は、ブロックの後では見えない
  • ブロックの中で、外と同じ名前を定義し直せる(シャドーイング)

スコープは、ブロックのような字句的な入れ子だけを扱います。

Kill とスコープ: Kill はスコープに関係なく、その名前を以降すべて見えなくします。外で定義した名前をブロックの中で del すると、ブロックを出た後も見えません。

NameSpec と Names

穴に入る名前は、名前空間ごとに用意した候補の中から選ばれます。候補の作り方を決めるのが NameSpec です。

正規表現で候補を作る

space(名前空間, 正規表現, 個数) で、正規表現に合う互いに異なる名前を、指定した個数だけ作ります。

#![allow(unused)]
fn main() {
fn names() -> NameSpec {
    NameSpec::new()
        .space(VAR, "[a-c]", 3)
        .space(FUNC, "[a-c]", 3)
}
}

名前空間を複数使うときは .space を続けて書きます。

候補は proptest が作ります。そのため、失敗した入力を縮小すると、名前も正規表現の範囲で短く単純なものになります。

Strategy を渡す

正規表現で書けない候補は、space_with で Strategy を直接渡します。予約語と重なる名前を避けたいときに使用します。

#![allow(unused)]
fn main() {
const KEYWORDS: [&str; 5] = ["let", "print", "del", "fn", "call"];

fn names() -> NameSpec {
    let var = prop::collection::hash_set(
        "[a-z]{1,4}".prop_filter("keyword", |s| !KEYWORDS.contains(&s.as_str())),
        3,
    )
    .prop_map(|set| set.into_iter().collect::<Vec<_>>());
    NameSpec::new().space_with(VAR, var.boxed())
}
}

固定の候補

候補を固定したいときは、space_with に proptest の Just を渡します。特定の名前で起きるバグを再現したいときや、単体テストに向いています。

#![allow(unused)]
fn main() {
let names = NameSpec::new().space_with(VAR, Just(vec!["x".to_string(), "y".to_string()]).boxed());
}

候補の数の決め方

候補の数は生成される入力の性質を大きく変えます。

少ないときは同じ名前が何度も使われます。再定義やシャドーイング、同じ名前の削除と再定義が自然に起こり、名前解決器にとって難しい入力になります。

多いときは名前がばらけて関係が単純になります。名前どうしの衝突で起きるバグは見つかりにくくなります。

一方で、少なすぎると制約を満たせなくなります。

  • distinct_defs(再定義なし)は、定義の数が候補の数を超えると満たせない
  • 「見えていない名前を参照する」は、その時点ですべての候補が見えていると満たせない

満たせない入力は棄却されるので、棄却が多いときは候補の数を見直してください。

Binds と規則

名前どうしの関係は規則として書きます。規則は &Binds を受け取って Z3 の Bool を返す関数で、fill に渡します。

#![allow(unused)]
fn main() {
program().fill(names(), |binds| bound(binds, VAR))
}

この節では、規則の材料になる Binds と、よく使う関係を表す述語を説明します。

Bind: 穴の番号

Binds は、骨格の穴を評価順に並べたものです。規則の中では、穴を評価順の番号 i で指します。番号が小さいほど先に評価されるので、「i より前の穴」は番号の大小で表せます。

穴の番号は名前空間と役割で取り出します。どれも評価順に並んだ番号を返します。

書き方取り出す穴
binds.defs(S)名前空間 S の Def
binds.uses(S)名前空間 S の Use
binds.kills(S)名前空間 S の Kill
binds.refs(S)名前空間 S の参照(Use と Kill)
binds.of(S, role)名前空間 S の、役割 role の穴

binds.name[i] は穴 i に入る名前を表す Z3 の Int です。値は候補の番号なので、binds.name[p] == binds.name[q] で「穴 p と穴 q に同じ名前が入る」と書けます。

#![allow(unused)]
fn main() {
// VAR の定義の名前は、すべて異なる
fn no_redefinition(binds: &Binds) -> Bool {
    constraint!(
        distinct(binds.defs(VAR).map(|i| &binds.name[i])),
    )
}
}

生成時に決まる関係

ステップやスコープは構造を作った時点で決まっています。このような関係は Z3 の Bool ではなく、 Rust の値 (bool や usize) で返されます。

書き方意味
binds.same_step(p, q)穴 p と q が同じステップにある
binds.encloses(outer, inner)穴 outer で定義した名前が、穴 inner から見える範囲にある
binds.boundaries_between(outer, inner)穴 inner から穴 outer の定義まで、越えるクロージャの数(クロージャを参照)

Rust の bool なので、constraint! の中では if で制約を絞るのに使います。

#![allow(unused)]
fn main() {
// 同じステップの中では、参照と定義に違う名前を使う
constraint!(for p in binds.uses(VAR) {
    for q in binds.defs(VAR) {
        if binds.same_step(p, q) {
            binds.name[p] != binds.name[q]
        }
    }
})
}

束縛の述語

名前解決でよく使用する関係は関数として用意されています。どれも Z3 の Bool を返すので、constraint! の中でそのまま組み合わせられます。

書き方意味
visible(binds, i)参照 i が、見えていて削除されていない定義を指す
resolves_to(binds, i, k)参照 i が、定義 k を指す(同名の定義のうち評価順で最後のもので、間に削除がない)
killed(binds, i)参照 i が、削除済みの名前を指す
bound(binds, S)名前空間 S の参照が、すべて見えている
unbound(binds, S, n)名前空間 S の、見えていない参照がちょうど n 個
defined_in_same_step(binds, i)参照 i と同じステップに、同じ名前の定義がある
distinct_defs(binds, S)名前空間 S の定義の名前が、すべて異なる

「見えている」は、次をすべて満たすことです。

  • その名前の定義が、参照より前に評価される
  • その定義のスコープが、参照を囲む
  • 定義から参照までの間に、その名前が削除されていない

上の規則で足りないときは、次の2つを使って自分で制約を作れます。visible や resolves_to も、この2つの組み合わせで書かれています。

書き方返すもの
reaching_defs(binds, i)参照 i の候補の定義。同じ名前空間で、i より前にあり、i を囲むスコープにあるもの
kills_between(binds, k, i)k と i の間で、i と同じ名前空間の名前を削除している穴

参照の3つの状態

参照は、次の3つのどれかの状態にあります。

状態書き方
見えているvisible(binds, i)
削除済みkilled(binds, i)
未定義(!visible(binds, i)).given([!killed(binds, i)])

!visible は「削除済み」と「未定義」の両方を含みます。Getting Started の異常系を del を含む言語でそのまま使うと、削除済みの名前を使う入力も「未定義」として生成されます。

given は前提が成り立つときだけ条件を問う書き方です。詳細はラベルで説明します。

ラベル

規則の中で生成した入力にラベルを付けられます。ラベルは次の3つの用途があります。

  • どの穴を、どの種類の誤りとして壊したかを記録する(mark)
  • 制約にはせず、生成された入力を分類する(observe)
  • 制約に名前をつけ、棄却の原因を調べる(require)

ラベルには Copy + Debug + PartialEq を実装した任意の型を使用できます。

#![allow(unused)]
fn main() {
/// 規則で壊した種類
#[derive(Debug, Clone, Copy, PartialEq)]
enum Bug {
    Unbound, // 未定義の名前を使う
    Killed,  // 削除済みの名前を使う
}

/// 生成された入力の分類
#[derive(Debug, Clone, Copy, PartialEq)]
enum Shape {
    Redefined, // 同じ名前の定義が2回以上ある
}
}

mark: 壊した場所を記録する

binds.mark(i, kind, cond)は、cond をそのまま返し、同時に「cond が成り立つなら、穴 i は kind として壊れている」を記録します。

#![allow(unused)]
fn main() {
|binds| constraint!(
    exactly(1) { for i in binds.refs(VAR) {
        binds.mark(i, Bug::Unbound, !visible(binds, i))
    } },
)
}

解いた後は、 s.marks::<Bug>() で (穴, ラベル) の列を受け取ります。ここでは「壊れているのがちょうど1箇所」しか扱わないため、次のような取り出す関数を用意しておくと便利です。

#![allow(unused)]
fn main() {
fn the_mark(s: &Solved) -> (usize, Bug) {
    let [(hole, bug)] = s.marks::<Bug>()[..] else {
        panic!("one mark expected: {s:?}")
    };
    (s.span(hole).start, bug)
}
}

given: 違反条件の重複を避ける

ある違反を起こすと、別の違反も必ず起きてしまうことがあります。例えば、関数の呼び出しに「未定義の関数を呼ぶ」と「引数の数が合わない」の2種類の違反を用意したとします。引数の数の違反を「見えている定義と数が合わない」と書くと、未定義の関数の呼び出しは、引数の数の違反も同時に満たします。

違反を種類ごとに数えると、未定義の関数を呼ぶ入力では違反が2つ数えられます。そのため exactly(1) で1か所だけ壊そうとすると、この入力は作れず、一度も生成されません。

#![allow(unused)]
fn main() {
#[derive(Debug, Clone, Copy, PartialEq)]
enum CallBug {
    Unbound,
    ArityMismatch,
}

// 未定義の呼び出しは ArityMismatch も満たすので、Unbound が一度も出ない
|binds| constraint!(
    exactly(1) {
        for i in binds.uses(FUNC) { binds.mark(i, CallBug::Unbound, !visible(&binds, i)) },
        for i in binds.uses(FUNC) { binds.mark(i, CallBug::ArityMismatch, arity_mismatch(&binds, i)) },
    },
)
}

引数の数の違反を、given で「関数が見えているとき」に限って問うと、2つの違反を1つずつ独立に作れます。

#![allow(unused)]
fn main() {
|binds| constraint!(
    exactly(1) {
        for i in binds.uses(FUNC) { binds.mark(i, CallBug::Unbound, !visible(&binds, i)) },
        for i in binds.uses(FUNC) {
            binds.mark(i, CallBug::ArityMismatch, arity_mismatch(binds, i).given([visible(&binds, i)]))
        },
    },
)
}

cond.given([前提..]) は、cond とすべての前提の論理積を表します。したがって、前提が偽なら式全体も偽です。前提が成り立つ場合に cond も成り立つことを要求したいときに使用します。

一度も出ないラベルの警告

一度も真にならなかったラベルは、テストの終わりに警告されます。テストは通っていても、狙った入力が一度も生成されなかったことを知らせるためです。

原因は大きく2つあります。作れないか、出にくいかです。

作れない場合:

  • 構造が足りない: 削除の後に参照が来る構造がなければ、削除後の参照は作れません。Strategy 側で、その構造を用意します
  • 違反が重複する: ある違反が別の違反も満たすため、exactly(1) では片方だけの入力を作れません。given で条件を分けます
  • 他の制約で禁じている: bound などで起こらないようにした種類まで mark すると、そのラベルは付きません
  • 名前候補が偏っている: 候補が少ないと未定義参照を作れず、多すぎると再定義などの衝突が起きにくくなります

出にくい場合:

  • 条件が稀: observe で記録する条件は分布を変えないため、生成されたケース数の範囲では一度も真にならないことがあります。構造の出やすさを調整するか、その種類だけを狙うテストを分けます

迷ったら、その種類だけを exactly(1) で狙うテストを書きます。すべて棄却されるなら作れません。require に名前を付け、take_rejections でどの制約に当たったかを調べます。

observe: 分類する

binds.observe(kind, cond)は、cond を制約にはせず、生成された入力で cond が成り立ったかどうかだけを記録します。生成される入力の分布は変わりません。

observe は Bool を返さないので、constraint! の中には書けません。規則の本体で先に呼んでおき、制約は別に返します。

#![allow(unused)]
fn main() {
fn bound_observing_redefinition(binds: &Binds) -> Bool {
    binds.observe(Shape::Redefined, !distinct_defs(binds, VAR));
    bound(binds, VAR)
}
}

記録したラベルは、s.labels::<L>() や s.has(kind) で確認できます。次のテストは、Shape::Redefined が付いた入力に、実際に同じ名前の定義が2回以上あるかを確かめています。

#![allow(unused)]
fn main() {
proptest! {
    #[test]
    fn observe_classifies(s in program().fill(names(), bound_observing_redefinition)) {
        let defs: Vec<&str> = s.holes()
            .filter(|(_, h)| h.space == VAR && h.role == Role::Def)
            .map(|(_, h)| h.name.as_str())
            .collect();
        let unique: HashSet<_> = defs.iter().collect();
        prop_assert_eq!(s.has(Shape::Redefined), unique.len() < defs.len(), "{:?}", s);
    }
}
}

出現回数と未出現の警告

それぞれのラベルは、何回出現したかが数えられています。

#![allow(unused)]
fn main() {
eprintln!("{:?}", label_stats());
}

label_stats() はラベルごとの出現回数を返します。take_label_stats() は返し、カウントをリセットします。回数はスレッドごとに数えられます。

一度も現れなかったラベルは、テストのスレッドが終わるときに標準エラーへ警告されます。テストが通っていても表示されます。

proptest-z3 warning: label `Killed` never occurred in 259 cases (test `tests::my_test`); is it implied by another violation? consider `given`

require: 棄却の原因を調べる

構造が制約を満たせないと、生成は棄却されます。棄却が多いときは、require で原因を調べます。

binds.require(label, cond) は、cond に名前を付けて制約に加えます。mark と違って値を返さないので、constraint! の中には書かず、規則の本体で呼びます。

規則の戻り値は名前のない制約で、棄却の理由には出ません。名前のない制約と矛盾したときは、名前付きの側だけが理由に出ます。調べたい制約はすべて require に移し、戻り値は Bool::from_bool(true) にします。同じ制約を require しつつ戻り値にも入れると、そのラベルは理由に出なくなります。

次の規則では、自己参照を含み、すべての参照が見えていて、再定義のない入力を求めています。

#![allow(unused)]
fn main() {
fn rule(binds: &Binds) -> Bool {
    binds.require("self_ref", constraint!(any { for i in binds.uses(VAR) { defined_in_same_step(binds, i) } }));
    binds.require("all_bound", bound(binds, VAR));
    binds.require("no_redefinition", distinct_defs(binds, VAR));
    Bool::from_bool(true)
}
}

自己参照の右辺を見えるようにするには、同じ名前の定義が前に必要です。しかし、それは再定義にもなるため、3つの制約を同時には満たせません。このような矛盾は、take_rejections() に現れるラベルの組から見つけられます。

Z3 が返す組は最小とは限らず、原因と関係のない制約が含まれることもあります。疑わしい制約を1つずつ外し、棄却が解消するか確かめます。

fill と Solved

fillで骨格の Strategy と名前の候補と規則をまとめて、穴を埋めた入力の Strategy にします。生成される値は Solved です。

#![allow(unused)]
fn main() {
proptest! {
    #[test]
    fn defined_names_resolve(s in program().fill(names(), |binds| bound(binds, VAR))) {
        prop_assert_eq!(undefined_refs(&s.text), vec![], "{:?}", s);
    }
}
}

解き方を選ぶ

fill_with を使用すると、穴の埋め方を選択できます。既定では fill は Fill::Greedy を使用します。

解き方内容
Fill::Greedy(既定)ヒントを仮定として解き、制約と衝突したら、衝突したヒントのうち最後のものを捨てて解き直す
Fill::Optimal守れるヒントの数が最大になるように解く

どちらの解き方でも、同じ骨格とヒントからは同じ結果が得られます。縮小の途中で同じ入力を解き直しても、結果は変わりません。

  • Fill::Greedy は速いのが利点です。ただし、捨てるヒントの選び方が最適とは限らないので、Fill::Optimal より多くのヒントを捨てることがあります。

  • Fill::Optimal はヒントにできるだけ忠実です。その分、穴が多いと遅くなります。

基本は Fill::Greedy を使用し、生成される名前の偏りが気になる場合に Fill::Optimal を試してください。

縮小

テストが失敗すると、proptest は入力を縮小します。 proptest-z3 の縮小は、構造・ヒント・名前の候補を縮めながら、規則を満たす入力だけを試します。

  • 縮めた入力が規則を満たせないときは、別の縮め方を探す
  • 解いた結果が以前に試したものならば、テストを呼ばない
  • 縮めた入力が以前と同じならば、解き直さない

縮小は、これ以上縮まなくなるまで繰り返すことはしません。原因が読み取れる大きさまで縮めば十分という方針です。

縮小では入力が変わるたびに Z3 が呼ばれるので、縮小には通常の proptest より時間がかかります。

Solved: 埋めた結果を使用する

Solved は穴を埋めた結果です。Z3 の型を含まないので、テストの本体では Z3 を意識する必要はありません。

よくあるパターン

この章では、名前解決のテストでよく使う制約の書き方を紹介します。制約を作る参考にご活用ください。

名前解決の境界条件

ランダムに作った正常系では、名前解決器が間違えやすい状況はめったに出てきません。bound で正常系にしたうえで、そうした状況を any で必ず含めます。

外に同じ名前がある

let x
let x = x       // 右辺は1行目の x を指す

誤って左辺の x を先に登録してしまう名前解決器は、右辺の自分自身に結び付けてしまいます。

program().fill(names(), |binds| constraint!(
    bound(binds, VAR),
    any { for i in binds.uses(VAR) { defined_in_same_step(binds, i) } },
))

bound の下では、すべての参照が見えている、そのうえで同じステップに同じ名前の定義があるので、右辺は必ず外側の定義を指します。

シャドーイング

let x
{
    let x
    print x     // 内側の x を指す
}

外側の x も名前は一致するので、スコープを正しく辿らない名前解決器は外側を選んでしまいます。

/// 参照 `i` が指す定義が、外側のスコープにある同じ名前の定義を隠している
fn hides_outer(binds: &Binds, i: usize) -> Bool {
    let cases: Vec<Bool> = reaching_defs(binds, i)
        // i が見える可能性のある定義の列挙
        .flat_map(|k| reaching_defs(binds, i).map(move |q| (k, q))) 
        // q が k より外側にある(同じスコープは含まない)
        .filter(|&(k, q)| !binds.encloses(k, q)) 
        // i が実際に k を指す、同じ名前のもの
        .map(|(k, q)| constraint!(resolves_to(binds, i, k), binds.name[q] == binds.name[k]))
        .collect();
    Bool::or(&cases)
}

program().fill(names(), |binds| constraint!(
    bound(binds, VAR),
    any { for i in binds.uses(VAR) { hides_outer(binds, i) } },
))

テスト

どちらの例も、名前解決の結果を Solved::target と比べます。

let resolved = resolve(&s.text);    // 参照の位置 → 定義の位置
for (hole, filled) in s.holes().filter(|(_, h)| h.role.is_ref()) {
    let expected = s.target(hole).map(|def| s.span(def).start);
    prop_assert_eq!(resolved.get(&filled.span.start).copied(), expected, "{:?}", s);
}

定義へのジャンプや参照検索のような「どこを指すか」を返す機能も、同じ形でテストが可能です。

巻き上げ

Rust の関数宣言のように、後ろで定義した名前も、同じスコープの前の位置から見える言語があります。これを「巻き上げ」と呼びます。

call f      // まだ定義されていないが、呼べる
fn f

visible や bound は「評価順で前の定義だけが見える」という規則で書かれています。そのため巻き上げのある名前空間では、可視性の規則を自分で書く必要があります。

/// 参照 `i` から、前後に関係なく、囲むスコープにある同じ名前の定義が見える
fn hoisted(binds: &Binds, i: usize) -> Bool {
    let defs: Vec<Bool> = (0..binds.len())
        .filter(|&k| binds.role[k] == Role::Def && binds.space[k] == binds.space[i])
        .filter(|&k| binds.encloses(k, i))
        .map(|k| constraint!(binds.name[k] == binds.name[i]))
        .collect();
    Bool::or(&defs)
}

正常系では、すべての呼び出しが巻き上げで見えていることを要求します。そのうえで、巻き上げがなければ見えていない呼び出し(前方参照)を必ず含めます。

program().fill(names(), |binds| constraint!(
    bound(binds, VAR),
    all { for i in binds.refs(FUNC) { hoisted(binds, i) } },
    // 前方参照が少なくとも1つある
    any { for i in binds.refs(FUNC) { hoisted(binds, i) & !visible(binds, i) } },
))

ここでは、既存の visible を「順序ありの可視性」として使用しています。hoisted が真で visible が偽なら、巻き上げによって初めて見える、ということです。

再帰と let rec

ここでは、同じ言語に次の両方があり、処理系がそれぞれを正しく扱うかを確かめます。

fn f {
    call f      // 非再帰の関数なら、ここから f は見えない
}
fn rec g {
    call g      // 再帰の関数なら見える
}

再帰かどうかは、制約ではなくステップの切り方で決まります。

  • ステップの中では、Def が評価順の最後に回る
  • 名前と本体を1つのステップにすると、本体から名前は見えない(非再帰)
  • 名前だけのステップを本体より前に置くと、本体から見える(再帰)
fn stmt() -> impl Strategy<Value = Vec<Frag>> {
    let simple = prop_oneof![
        VAR.def().prop_map(|x| vec![frag!["let ", x, "\n"]]),
        VAR.refer().prop_map(|y| vec![frag!["print ", y, "\n"]]),
        FUNC.refer().prop_map(|f| vec![frag!["call ", f, "\n"]]),
    ];
    simple.prop_recursive(3, 16, 4, |inner| {
        let body = prop::collection::vec(inner, 1..4).prop_map(|stmts| stmts.concat());
        (any::<bool>(), FUNC.def(), body).prop_map(|(rec, f, body)| {
            let body = frag![" {\n", Frag::scope(body), "}\n"];
            if rec {
                vec![frag!["fn rec ", f], body]   // 名前のステップ → 本体のステップ
            } else {
                vec![frag!["fn ", f, body]]       // 1つのステップ
            }
        })
    })
}

fn program() -> impl Strategy<Value = Skeleton> {
    prop::collection::vec(stmt(), 1..8).prop_map(|stmts| Skeleton::steps(stmts.concat()))
}

テストは「名前解決の境界条件」と同じく Solved::target と比べます。

注意点

fn rec f { call g } and g { call f }

のような相互再帰はこの方法では作れません。f の本体はテキスト上の g の定義より前にあるのに、g を見る必要があるからです。これは「グループの中だけの巻き上げ」なので、前の節の hoisted の候補を、そのグループの定義に絞って書きます。

クロージャ

let x
let g = || {
    let h = || {
        print x     // 2段のクロージャを越えて x をキャプチャする
    }
}

クロージャの外の名前を参照すると、処理系はその名前をクロージャの中へ持ち込む必要があります(キャプチャ)。ここではキャプチャされる参照を処理系が正しく見つけるかを確かめます。

骨格

ブロックとクロージャは可視性の規則が全く同じです。違うのは「ここで実行時のフレームが変わる」という点だけです。この違いを表すために、クロージャ本体は Frag::scope の代わりに Frag::boundary で作ります。

fn closure(f: Frag, stmts: Vec<Frag>) -> Frag {
    frag!["let ", f, " = || {\n", Frag::boundary(stmts.into_iter().map(|s| frag![s, "\n"])), "}"]
}

2段の入れ子の中の参照は、ランダムな形ではめったに生まれません。専用の骨格を用意します。

fn program_with_nested_closures() -> impl Strategy<Value = Skeleton> {
    let head = prop::collection::vec(VAR.def().prop_map(|x| frag!["let ", x]), 1..3);
    let deep = (VAR.def(), VAR.def(), VAR.refer()).prop_map(|(g, h, u)| {
        closure(g, vec![closure(h, vec![frag!["print ", u]])])
    });
    (head, prop::collection::vec(stmt(), 0..5), deep).prop_map(|(head, body, deep)| {
        Skeleton::steps(head.into_iter().chain(body).chain([deep]).map(|s| frag![s, "\n"]))
    })
}

制約

rules::captured(binds, i) は、参照 i が境界の外の定義を指すことを表します。何段の境界を越えるかは binds.boundaries_between(k, i) で数えられるので、2段以上越えるキャプチャも自分で書けます。

/// 参照 i が、2段以上のクロージャを越えて定義を指す
fn relayed(binds: &Binds, i: usize) -> Bool {
    let cases: Vec<Bool> = reaching_defs(binds, i)
        .filter(|&k| binds.boundaries_between(k, i) >= 2)
        .map(|k| resolves_to(binds, i, k))
        .collect();
    Bool::or(&cases)
}

ここで名前の一致ではなく resolves_to を使用しているのは、シャドーイングのためです。

let x
let g = || {
    let x
    print x    // 内側の x を指す。キャプチャではない
}

テスト

すべての参照に、キャプチャかどうかの印を付けます。mark の戻り値は捨てているので、制約にはなりません。

#[derive(Debug, Clone, Copy, PartialEq)]
struct Captured;

proptest! {
    #[test]
    fn captures_are_found(s in program_with_nested_closures().fill(names(), |binds| {
        for i in binds.refs(VAR) {
            binds.mark(i, Captured, captured(binds, i));
        }
        constraint!(
            bound(binds, VAR),
            any { for i in binds.refs(VAR) { relayed(binds, i) } },
        )
    })) {
        let expected: HashSet<usize> =
            s.marks::<Captured>().into_iter().map(|(hole, _)| s.span(hole).start).collect();
        prop_assert_eq!(captures(&s.text), expected, "{:?}", s);
    }
}

注意点

  • captured は、トップレベルの定義への参照もキャプチャに数えます。グローバル変数をキャプチャと呼ばない言語では、期待値を作るときに除いてください。
  • captured は順序ありの可視性に従います。巻き上げる名前空間では使えません。

A.2 ステップ・評価順・スコープの規則

ステップ

  • ステップは「定義が見えるようになる単位」で、言語の文に当たります。
  • ステップを作るのは Skeleton::steps(..) / Frag::scope(..) / Frag::boundary(..) の3つだけです。どれも、渡された各要素を1ステップとして閉じます。
  • frag! / Frag::concat / Frag::join はステップを作りません。連結した断片は、外側で閉じられたときに同じ1ステップになります。
  • Frag::scope(..) / Frag::boundary(..) の中の穴は中のステップに属し、外側の文のステップには属しません。

評価順

評価順は次の規則で決まります。

  1. ステップはテキスト順に並びます。
  2. 1つのステップの中では、
    • 先: Use の穴と、そのステップに含まれる入れ子スコープ内の穴(テキスト順)
    • 後: そのステップ自身の Def と Kill の穴(テキスト順)

帰結:

  • let x = x の右辺 x(Use)は、同じ文の左辺 x(Def)より先に評価されるので、それを指しません。
  • del x(Kill)は、同じ文の Use より後に評価されます。
  • fn f { .. call f .. } のように、文の Def とその文に含まれるスコープを並べると、スコープ内の穴はすべて f の定義より先に評価されます。そのため、既定では再帰呼び出しは見えません。 境界(Frag::boundary)でも同じです。
  • 境界の中身(クロージャの本体)は、書かれた位置で評価されたものとして扱われます(その場で呼ばれたのと同じ)。境界の中の Kill は、境界の後の参照にも効きます。

スコープ

  • Frag::scope(steps) が入れ子のスコープを1つ作ります。スコープは字句的(静的)な入れ子だけです。
  • スコープ内の Def は、そのスコープとさらに内側のスコープからだけ見えます。外側と兄弟スコープからは見えません。
  • 外側の Def は内側から見えます。内側で同名を定義すると、内側ではそちらが優先されます(シャドーイング)。
  • スコープは z3 に渡されません。Rust 側の bool(Binds::encloses)として、制約を組み立てるときに候補を絞るのに使われます。

境界(クロージャ・関数本体)

  • Frag::boundary(steps) は、境界の印が付いたスコープを作ります。クロージャや関数の本体に使います。
  • 見える範囲(encloses、visible、target など)は Frag::scope と全く同じです。境界は名前解決の結果を変えません。
  • 違いは、参照が境界を何個越えて定義に届くかを数えられることだけです(Binds::boundaries_between)。これを使って「キャプチャ」(captured)を判定します。
  • 普通のスコープ(Frag::scope)は越えても数えません。境界の中のブロック、ブロックの中の境界は、どちらも自由に入れ子にできます。

各 API がスコープを跨ぐか

  • 跨がない: 同じステップの中だけ(同じステップの穴は必ず同じスコープにある)

Kill はスコープを跨ぎます。 定義 k から参照 i までの間(評価順)に、同じ名前空間・同じ名前の Kill が1つでもあれば、k は i から見えなくなります。その Kill がどのスコープにあるかは問いません。

  • 内側のスコープで del a すると、外側の a も消えます。内側に同名の a があって、del a がそちらを指していても同じです。
  • 閉じた兄弟スコープの中の del a も、後の a の参照に効きます。
  • Kill の後に同名の Def があれば、その定義は新しく見えます。ただし、見える範囲はその Def のスコープの中だけです。

distinct_defs はスコープを跨ぎます。 !distinct_defs(binds, S) は「どこかに同名の定義の組がある」という意味で、同じスコープでの再代入に限りません。同じスコープの中での再定義だけを禁じたい・許したい場合は、binds.encloses と binds.same_step で定義の組を絞り、constraint! で自分で書きます。

制約の材料になる関数(イテレータを返し、z3 の式ではありません):

シグネチャスコープ内容
reaching_defs(binds: &Binds, i: usize) -> impl Iterator<Item = usize>字句的i が指し得る定義の候補。k < i、Def、i と同じ名前空間、encloses(k, i) を満たす k(評価順)

resolves_to(i, k) は Solved::target を制約にしたものです。解いた後に target(i の穴) == Some(k の穴) となるのは、resolves_to(i, k) が真のときだけです。visible(i) は「reaching_defs(i) のどれかに resolves_to」と同値です。

参照の3状態

参照 i は次のどれか1つになります。!visible は「削除済み」と「未定義」の和です。

状態式
見えているvisible(binds, i)
削除済みkilled(binds, i)
未定義(どこにも見える定義がない)(!visible(binds, i)).given([!killed(binds, i)])

「未定義」には、外側から見えない定義(閉じたスコープの中・兄弟スコープの中)しかない場合も含まれます。「スコープ外の定義を指している」と「どこにも定義がない」を区別したいときは、binds.defs(..) を encloses で絞り、constraint! で自分で書きます。

よく使う形

#![allow(unused)]
fn main() {
// 正常系
bound(binds, VAR)

// 再定義を含む正常系(スコープを跨いだ同名も含む)
constraint!(bound(binds, VAR), !distinct_defs(binds, VAR))

// 異常系: 参照がちょうど1つ見えない。その穴に印を付ける
constraint!(exactly(1) { for i in binds.refs(VAR) {
    binds.mark(i, Bug::Unbound, !visible(binds, i))
} })

// 自己参照(`let x = x`)
constraint!(all { !visible(binds, i), defined_in_same_step(binds, i) })

// 定義 k が使われている(未使用の定義の検出に。`!` を付けると未使用)
constraint!(any { for i in binds.refs(VAR) { resolves_to(binds, i, k) } })

// キャプチャされた参照に印を付ける(分類なので制約にはしない)
for i in binds.refs(VAR) {
    binds.mark(i, Captured, captured(binds, i));
}

// 境界を2つ以上越えるキャプチャ(外側のクロージャが中継する)が少なくとも1つある
fn relayed(binds: &Binds, i: usize) -> Bool {
    let cases: Vec<Bool> = reaching_defs(binds, i)
        .filter(|&k| binds.boundaries_between(k, i) >= 2)
        .map(|k| resolves_to(binds, i, k))
        .collect();
    Bool::or(&cases)
}
constraint!(bound(binds, VAR), any { for i in binds.refs(VAR) { relayed(binds, i) } })
}

境界の数で条件を変えたいときは、captured を使わずに、relayed のように reaching_defs を boundaries_between で絞って resolves_to を並べます。

A.14 テストを書くときの確認事項

LLM がテストを書くときに間違えやすい点です。

  • 制約の中の番号は評価順、Solved の Hole はテキスト順。制約の中で Hole は作れない。
  • 同じ文の右辺は左辺の定義を見ない。文の Def は、その文に含まれるスコープからも見えない(既定では再帰できない)。
  • Kill はスコープを跨いで同名をすべて消す。
  • distinct_defs はスコープを跨いで数える。!distinct_defs は「どこかに同名の定義がある」で、同じスコープでの再代入とは限らない。
  • Frag::boundary は見える範囲を変えない。外側の定義はクロージャの中から普通に見える。キャプチャかどうかは captured / boundaries_between で判定する。
  • boundaries_between は普通のスコープ(Frag::scope)を数えない。ブロックの中から外側の定義を指しても、キャプチャにはならない。
  • 境界の中身は書かれた位置で評価されたものとして扱う。クロージャ本体の Kill は、その後の参照にも効く。
  • 「未定義」を他の違反と区別するには given で前提を足す。そうしないと、ある種類が一度も生成されないことがある(警告で気づける)。
  • mark の戻り値を制約に入れ忘れると、ただの記録になる。
  • 異常系の exactly(1) は、対象の穴が骨格に1つもないと unsat。形の側で対象の穴を確実に作る。
  • 正常系の検査器(テストの期待値)は、rules と独立に書く。同じ意味論で書くと同じ誤りを共有する。
  • 規則のクロージャは 'static。外の値は move で取り込む。
  • require は値を返さないので constraint! の中に書かない。規則の本体で呼び、同じ制約を戻り値に重ねて入れない。
